# Повторная проверка и очистка кода — 5 ноября 2026 года

Проверены очередь команд, остановка и обновление процесса, роли, добавление людей,
границы пространств и неиспользуемый код. Это проверка кода с подставными API;
реальные публикации в MAX и Telegram не выполнялись.

## Что исправлено

- Текстовые события раньше распознавались как повторные по хешу всего события.
  Изменение имени отправителя или служебного поля маршрутизации меняло хеш.
  Новые записи используют ID сообщения и отправителя; callback по-прежнему
  распознаётся по `callback_id`.
- После истечения срока корректной остановки защищённые через `shield` задачи
  могли продолжать работу после отмены внешних работников. Теперь бот отменяет
  оставшиеся операции и ждёт завершения их очистки до закрытия HTTP и SQLite.
- Проверка Git по таймауту или отмене оставляла подпроцесс работать. Теперь
  асинхронная проверка завершает процесс; на Linux — всю его группу, включая
  `git-remote-https`/`ssh`, и собирает результат перед выходом.
- Ввод ID участника принимал ноль, ведущие нули и не-ASCII цифры. Теперь
  используются положительные десятичные ID. Форма добавления не меняет роль
  уже существующего участника: для этого есть отдельное меню с подтверждением.

## Удалённые остатки старой версии

Удалены генерация и погашение одноразовых приглашений, метод `invite_link`,
связанные константы, создание новой таблицы `invites` и неиспользуемый импорт.
В рабочем MAX-адаптере приглашения не создавались: метод возвращал `None`,
а `redeem_invite` вызывался только тестами с подставным Telegram-получателем.

Кнопка заменена на «Добавить человека» по ID, доступную в каждом пространстве,
включая основное. Старые payload кнопок `inv`, `invn` и `space_member`
поддерживаются как переход к действующей форме. Таблица `invites`, если она
осталась в старой базе, не удаляется автоматически; программа её не использует.

Старые тесты неиспользуемых приглашений заменены проверками добавления людей,
неверных ID, прав администратора и совместимости старых кнопок.
В `env.example` значение `EMPLOYEE_CONFIRM=reaction` заменено на `text`;
существующее `reaction` продолжает означать текстовое подтверждение MAX.

## Что следует менять отдельно

1. `core.py` содержит более двух тысяч строк. Стоит вынести хранение, публикацию
   и управление людьми в отдельные модули. Делить нужно с сохранением сценарных
   тестов, поскольку эти части участвуют в защите от дублей и частичной публикации.
2. Пространства используют `ContextVar` и прокси общих объектов. Это изолирует
   параллельные задачи, но усложняет сопровождение. При дальнейшем развитии лучше
   явно передавать объект пространства сервисам и перейти от копирования схемы
   основного SQLite к версионируемым миграциям каждой базы.
3. Очередь материалов общая и последовательная. Для нескольких активных команд
   полезен ограниченный параллелизм по пространствам с общим лимитом ffmpeg и
   нейросети. Увеличивать число работников без этого нельзя: на VPS с 4 ГБ
   одновременные ролики заметно увеличат потребление памяти.
4. Ожидание ручной правки пока хранится в памяти. Сохранение этого состояния
   вместе с версией черновика позволит продолжать диалог после перезапуска.
5. В официальной схеме MAX рекомендуется webhook. Переход требует отдельной
   настройки HTTPS и приёма событий; существующий polling сохранён.

Код миграции старых черновиков и поддержка прежних настроек публикации оставлены:
они участвуют в обновлении существующей установки и не являются неиспользуемыми
функциями. Токены, группы и рабочие данные заново настраивать не требуется.

## Проверка изменений

Все **357 тестов прошли**. Отдельные регрессии проверяют повторную доставку
текстового сообщения с изменёнными метаданными, завершение защищённых операций
до возврата из `serve`, таймаут и отмену проверки Git, ввод ID и совместимость
старых кнопок. Проверки компиляции Python, синтаксиса `entrypoint.sh` и
`git diff --check` также прошли. Нагрузка настоящих пользователей и реальные
API в этой среде не проверялись.
