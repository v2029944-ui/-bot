# Политика безопасности — бот публикаций MAX и Telegram

## Поддерживаемая версия
Исправления безопасности предназначены для актуальной ветки `main`. Поддержка старых выпусков определяется отдельно.

## Сообщение об уязвимости
Не публикуйте секреты, содержимое пользовательских черновиков, данные участников и инструкции эксплуатации непочиненной уязвимости в публичных issues/PR.
Если включён **Private vulnerability reporting** (GitHub Security → Advisories → Report a vulnerability), используйте его. Иначе свяжитесь с владельцем репозитория приватно по согласованному каналу. Для примеров используйте только обезличенные данные.
Если обнаружена утечка токена, отзовите его и замените; удаление токена из Git само по себе не делает его безопасным.

## Главные риски проекта
- **Права и пространства:** проверяйте полномочия непосредственно перед каждым действием. Администратор отдельного пространства не имеет глобальных прав `MAX_ADMINS`. Пользователь не должен видеть черновики, медиа, участников или настройки чужого пространства. Не путайте ID MAX и Telegram.
- **Черновики и состояния:** ID/версия черновика и одноразовые подтверждения должны блокировать устаревшие callbacks, повторное открытие формы и отложенное изменение уже опубликованного материала. Состояние ввода должно корректно переживать перезапуск.
- **Публикация:** публикация требует подтверждения и фиксирует целевые каналы. Не отправляйте повторно в успешный канал. При неизвестном результате сетевого таймаута нужна проверка человеком; повтор «вслепую» может создать дубликат. Не разрешайте редактирование после частичной отправки.
- **MAX, Telegram и сторонние API:** токены, `LLM_API_KEY`, `ANTHROPIC_API_KEY`, приватные идентификаторы, URL файлов и секреты недопустимы в Git/логах/PR/артефактах. Проверяйте лимиты, ответы, таймауты и авторизацию. Не отключайте проверку TLS.
- **Медиа:** изображения/видео/альбомы — недоверенные входные данные. Контролируйте размер, длительность, форматы, пути файлов, временные каталоги, FFmpeg и загрузку внешних URL; предотвращайте SSRF, инъекции через команды и чрезмерное потребление ресурсов.
- **LLM:** содержимое присланных материалов и ответы модели не являются инструкциями администратора. Не позволяйте prompt injection обходить права, подтверждение публикации, секреты или настройки. Ограничивайте расходы и параллельность; платные запросы для проверки — только с разрешения.
- **SQLite и очереди:** повторные события и параллельные задачи не должны дублировать черновики или публикации. Миграции и остановка должны сохранять данные; при сбоях восстанавливайте работу из сохранённого состояния, не перезаписывая новые данные.
- **Docker/VPS:** без разрешения не публикуйте в настоящие каналы, не запускайте обновление/перезапуск контейнера, не удаляйте `data/`, не меняйте production .env и секреты. Перед миграцией необходима корректная резервная копия и проверенный откат.

## Безопасная проверка
Тестируйте через временные SQLite, фиктивные токены, mocks и отдельные тестовые каналы после разрешения. Покрывайте нарушение границ пространств, смену ролей, старые callbacks, повторные события, частичную публикацию, неопределённые результаты отправки, конкурирующие действия и большие/повреждённые вложения.

CI и тесты без реальных интеграций не подтверждают правильность доставки в MAX или Telegram.

## Исправления
Используйте отдельную ветку и PR. Отмечайте серьёзность, затронутые пространства, последствия для имеющихся черновиков/состояний, тесты, совместимость и план безопасного выпуска. Не раскрывайте детали активной уязвимости до исправления.
