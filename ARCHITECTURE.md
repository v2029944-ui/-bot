# Устройство бота

## Модули

`main.py` проверяет настройки, запускает MAX и фоновых работников, завершает
текущие операции перед закрытием HTTP и SQLite. `core.py` хранит настройки,
общее состояние и совместимый интерфейс функций. Сервисы загружаются по первому
обращению; их также можно импортировать напрямую.

| Модуль | Ответственность |
| --- | --- |
| `services/storage.py` | Черновики, статусы, очистка и восстановление |
| `services/media.py` | Фото, видео, превью и альбомы |
| `services/generation.py` | Промпты и запросы к провайдерам нейросетей |
| `services/submissions.py` | Приём материала и отправка на согласование |
| `services/review.py` | Правка, повторная генерация, выбор варианта и отклонение |
| `services/publication.py` | Подтверждение и публикация в каналы |
| `services/people.py` | Участники, роли и заявки |
| `services/menus.py` | Меню, правила и текстовый ввод |
| `services/monitoring.py` | Статус, баланс, уведомления и напоминания |
| `services/lifecycle.py` | Защита выполняемых операций при остановке |
| `dialog_state.py` | Постоянное состояние ожидания ввода |
| `resources.py` | Общие лимиты обработки медиа и запросов нейросети |
| `spaces.py` | Контекст и изоляция рабочих пространств |
| `max_.py`, `tg.py` | Адаптеры мессенджеров |
| `max_queue.py`, `max_actions.py` | Постоянные очереди материалов и команд |
| `comparison.py`, `post_footer.py` | Сравнение моделей и ссылка в посте |
| `ops.py`, `updater.py`, `entrypoint.sh` | Настройки, обновление и запуск |

## Очереди и параллельность

Событие MAX сохраняется до передачи следующего `marker`. Материалы получают
постоянный ключ по ID отправителя и сообщения. Команды пользователя выполняются
последовательно; разные пользователи обслуживаются до четырёх одновременно.

Очередь материалов запускает два работника по умолчанию (`MATERIAL_WORKERS=2`).
Перед выполнением запись переводится в `processing` синхронной операцией SQLite.
Другой работник исключает пространства с такой записью, поэтому одна команда
не получает две одновременные обработки. Во время сбоя одного материала другие
готовые к обработке материалы могут выполняться, пока он ожидает повторной попытки.

Контекст пространства передаётся через `ContextVar`, в том числе в `to_thread`.
База, пути, адаптеры и настройки во время операции относятся к этому пространству.
Общие ограничения на весь процесс: одна тяжёлая обработка медиа и до трёх
одновременных запросов нейросети. Для материалов можно включить один работник.

## Продолжение правок после перезапуска

В `dialog_state` каждой базы сохраняются ожидаемые ручные правки, комментарии,
причины отклонения, новые правила и поля настройки ссылки. Ключ включает тип
ввода, платформу и ID пользователя. Для поста сохраняются ID и версия, для
настройки — имя поля; копий текста поста и медиа в этой таблице нет.

Состояние удаляется после завершения/отмены ввода или через 7 дней. `/menu`
закрывает прежний ввод. После перезапуска маршрут ответа восстанавливается
из выбора пространства и состояния его базы. Перед применением правки
повторно проверяются права, версия, статус и результаты публикации.

Ожидание комментария сохраняется до завершения генерации. Если процесс
прерван, очередь может повторить сообщение в контексте того же черновика.
Если вариант уже изменился, повтор не заменяет его.

## Публикация и хранение

Публикация требует подтверждения администратора пространства. Перед отправкой в каждый канал записывается
неопределённый результат, после успешного ответа — успешный. Повтор пропускает
успешные каналы; неопределённый результат требует проверки человеком.
После частичной отправки редактирование блокируется.

После полной публикации администратор получает результат по каналам. Содержимое
черновика, файлы и сведения о каналах очищаются. Сохраняются компактные
идентификаторы, статус и даты для статистики и защиты от дублей. Необработанные файлы и временные
оригиналы очереди удаляются по срокам из [README.md](README.md#хранение).
Резервная копия включает `.env` и все базы/каталоги внутри `data`.

## Обновление

Обновление кнопкой загружает весь репозиторий, проверяет новую версию и
переключает код. Новые Python-модули входят в обновление автоматически.
Новые обязательные переменные окружения для этой структуры не нужны.
SQLite дополняется при запуске; существующие данные не пересоздаются.
Проверки запуска и возможность отката не заменяют резервную копию.

При сборке образа Docker копируется также весь `services/`; при ручном
обновлении нужно переносить все файлы архива. Инструкция: [INSTALL.md](INSTALL.md).

## Проверки

Набор тестов проверяет сценарии согласования и публикации, права, изоляцию
пространств, повторные события, продолжение ввода из нового процесса Python,
одновременную обработку разных команд, общие лимиты ресурсов и остановку.
HTTP API подменяются; обработка коротких видео проверяется настоящим ffmpeg.
Доступность настоящих каналов и отображение интерфейса требуют отдельной проверки.

## Ограничения

- Используется long polling. MAX рекомендует webhook для production;
  [настройка HTTPS и стоимость](WEBHOOK.md). Webhook в коде пока не реализован.
- Один процесс на одну базу и один MAX-токен. Несколько экземпляров с общей
  базой не поддерживаются.
- Отправка в MAX и Telegram не является общей транзакцией. При таймауте
  нельзя гарантированно определить результат без проверки канала.
- После аварии между доставкой черновика получателю и записью её результата
  возможно повторное личное превью того же черновика.
- Если ответ нейросети потерян при сбое, повтор генерации может оплачиваться
  провайдером как новый запрос.
- Формы создания пространства и добавления человека нужно открыть снова
  после перезапуска; постоянное ожидание ввода относится к перечисленным выше
  правкам постов, правилам и настройке ссылки.
- API-ключ и баланс нейросети общие для пространств.

Главный администратор может менять название, владельца и группы пространства
через меню без перезапуска. Настройки сохраняются после отдельного подтверждения;
изменение блокируется при незавершённой обработке или публикации. Данные
пространства сохраняются, прежний владелец теряет доступ, остальные участники
сохраняют права, а главные администраторы из `MAX_ADMINS` сохраняют доступ к №0.
Подробности — в [SPACES.md, «Изменение пространства»](SPACES.md#изменение-пространства).

Официальные контракты: [OpenAPI MAX](https://github.com/max-messenger/api-schema),
[Bot API MAX](https://dev.max.ru/docs-api/),
[Telegram Bot API](https://core.telegram.org/bots/api).

## Права на черновики

`services.people.can_manage_draft` проверяет активное пространство и адаптер,
а затем административную роль в этом пространстве. Авторство не даёт прав
на черновик: участники только отправляют материалы.
Проверка применяется к кнопкам, публикации, перегенерации, восстановленной ручной
правке и комментариям, спискам и отложенной доставке. Участники не меняют общие
правила, в том числе через обучение на комментариях.

Роли `emp`/`apr` читаются как `member` без перезаписи исходной роли в таблице
`people`, включая пространства; `adm` и владельцы сохраняются.
`MAX_APPROVERS` и `MAX_EMPLOYEES` остаются совместимыми списками участников,
а `MAX_ADMINS` задаёт администраторов. Поле адаптера `approvers` оставлено
для совместимости и содержит администраторов; оно не даёт права на конкретный пост.

Новый черновик, напоминания и предупреждения о сроке получают главные администраторы
из `MAX_ADMINS`. При пустом списке их получают администраторы пространства. Старые
отложенные доставки перенаправляются актуальным получателям. При запуске pending-материалы ставятся в существующую очередь
доставки администраторам, в том числе после обновления с авторского процесса.
Журнал MAX по получателю и версии позволяет не отправлять уже доставленные превью.
Администратор, начавший правку, получает новый вариант сразу, независимо от своего
режима уведомлений. Участникам остаются сообщения о публикации и отклонении.
Схема черновиков, версии, сохранённый ввод и очереди при миграции не удаляются.

Главные администраторы проверяются по исходному списку `MAX_ADMINS`, сохранённому
адаптером при старте. Роль `adm` из базы основного пространства не даёт права
создавать пространства или обновлять общий процесс.

Для подтверждённых/начатых публикаций поле `publication_channels` хранит снимок
получателей по платформам. Повтор с изменившимся набором каналов блокируется;
без уже выполненных отправок новое подтверждение обновляет снимок. Если Telegram
уже получил медиа, бот досылает текст в тот же чат. Для канала, заданного
через `@имя`, бот фиксирует числовой ID из ответа на отправку медиа.
Для старой записи без подтверждённого адресата досылка текста блокируется.
Администратор может закрыть незавершённую отправку. При завершении или закрытии
снимок каналов и содержимое черновика очищаются.

Кнопки сравнения моделей и ссылки задают желаемое состояние (вкл./выкл.), а не
инвертируют его. Старые toggle-кнопки только обновляют меню. Изменения сравнения
сериализованы внутри каждого пространства, включая сетевое получение каталога.


## Надёжность обновления и данных

`compatibility.json` объявляет версии формата, которые выпуск читает, и версию,
которую он записывает. Новый выпуск всегда должен читать формат текущего кода.
Для отката действует одно из двух условий: либо прежний выпуск сам читает новый
write-format, либо **исполняемый updater текущего Docker-образа** содержит явную
миграцию нового формата обратно в формат прежнего выпуска. Если нет ни прямой
совместимости, ни такой rollback-миграции, переключение кода блокируется до
`git reset`.

Переход data-v1 → data-v2 для lifecycle handoff использует второй вариант:
новый updater содержит миграцию 2→1, которая переводит состояния
`handoff`/`handoff_processing` в понятный v1 `pending`, сохраняя frozen payload.
Старый updater этой миграции не знает и поэтому обязан отказаться от установки v2.
Из-за этого первый переход на data-v2 требует сначала обновить Docker-образ с новым
`/app/updater.py`, не переключая рабочую папку `./code`, и только затем запускать
штатное GitHub-обновление.

Перед rollback сначала выполняется миграция данных и только после её успеха
переключается Git-код. Если миграция отсутствует или завершается ошибкой, код
на старую версию не переключается. Контракт совместимости не заменяет резервную
копию и не способен доказать семантическую корректность ошибочно объявленной
миграции — это проверяют интеграционные тесты.

Схема расширяется по PRAGMA table_info; ошибки I/O/readonly/locked не выдаются за
существующую колонку. Базы пространств имеют ту же версию схемы. Ошибка отдельного
пространства сохраняется как failed и не останавливает остальные; повторное
открытие идемпотентно, частично открытые ресурсы закрываются.

Подтверждение публикации хранит снимок получателей именно своего nonce/пользователя.
Подтверждения управления людьми также одноразовые и проверяют ревизию записи.
Локальные мутации правил и их результат фиксируются в одной транзакции по ключу
события команды: повтор после отмены возвращает ответ, не удаляя следующее правило.
Отложенная доставка использует lease, снимаемый после подтверждения или отмены;
после аварии lease восстанавливается при старте. Потеря ответа MAX всё ещё может
привести к повторному личному превью; это не повтор публикации в канал.

## Зависимости и проверки

Docker, проверка обновления и запуск используют один `requirements-dev.lock`
с полным деревом и хешами (он включает runtime, pytest, Ruff и mypy). Stamp учитывает
оба исходных requirements и оба lock-файла. При ошибке pip новый код не запускается;
во время probation делается одна попытка отката и восстановления зависимостей.
Если восстановление тоже не удалось, процесс завершается с ошибкой. Для установки
по сети всё ещё нужен доступ к реестру; атомарное переключение отдельных venv
пока не реализовано.

Обновление зависимостей в Python 3.12:

```sh
uv pip compile requirements.txt --generate-hashes --python-version 3.12 -o requirements.lock
uv pip compile requirements-dev.txt -c requirements.lock --generate-hashes --python-version 3.12 -o requirements-dev.lock
python -m pip install --require-hashes -r requirements-dev.lock
ruff check .
mypy
python -m pytest -ra
```

Прямые требования и lock-файлы изменяются вместе. После обновления библиотек
проверяются также Docker, PNG/JPEG, HEIC и видео. Разрешены только явно перечисленные
форматы изображений; FITS, PSD и прочие неиспользуемые декодеры не открываются.
Ресурсные пределы декодирования видео и реальную нагрузку VPS проверяют отдельно.

## MAX API2 и TLS

Основной URL адаптера — `https://platform-api2.max.ru`. `max_tls.create_ssl_context`
расширяет обычное доверие HTTPX публичным Russian Trusted Root CA из `certs/`.
Сначала проверяется SHA-256 сертификата по DER, затем сохраняются обычные CA и
настройки окружения HTTPX. Контекст передаётся только клиенту Bot API.
Отдельные клиенты CDN, Telegram и провайдеров нейросети его не используют.
Нет fallback на старый адрес или отключение проверки TLS при ошибке сертификата.

Docker копирует `max_tls.py` и `certs/`. Обновление из GitHub также получает эти
файлы вместе с кодом, поэтому отдельно устанавливать CA в ОС сервера не нужно.
Локальные TLS-тесты проверяют принятие доверенной цепочки, отказ при неизвестном
CA и неверном имени, сохранение настроенного CA-файла и отсутствие токена на CDN.
