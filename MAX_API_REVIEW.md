# Проверка совместимости с MAX

Дата повторной проверки: 5 ноября 2026 года. Проверены адаптер MAX, пространства, очереди, обработка медиа, согласование,
публикация в два канала и связанные тесты. Это проверка кода и контрактов API;
отправка сообщений в настоящий MAX не выполнялась: токен пока не предоставлен.

## Официальные источники

- [OpenAPI MAX, проверенная версия](https://github.com/max-messenger/api-schema/blob/1a4a502fab096aa3a15d83d7ea95667ffb44d2ac/schema.yaml).
- [Официальный Python SDK, проверенная версия](https://github.com/max-messenger/max-botapi-python/tree/4a286baa06d38f2db9f7244d94f89508743f8fee).
- [Документация Bot API](https://dev.max.ru/docs-api/).

Сайт dev.max.ru недоступен из среды проверки (HTTP 403), поэтому источником
сверки служит официальная схема из организации max-messenger на GitHub.
Репозиторий схемы обновлён перед проверкой. Возможные расхождения работающего
сервиса со схемой нужно проверять после получения токена.

## Найденные и исправленные ошибки

Повторная проверка после добавления пространств:

- Выбор пространства текстового ответа выполнялся при получении события, раньше
  обработки предыдущей кнопки. Быстрый ответ на «Править самостоятельно» мог попасть
  в собственное пространство вместо открытой правки другой команды. Теперь новые
  текстовые команды маршрутизируются внутри последовательной очереди пользователя.
  Пространство входящих фото/видео фиксируется до подтверждения marker, как прежде.
- Команда `/menu` из группы могла отменять незавершённый личный ввод. Групповые
  сообщения больше не изменяют контекст личного диалога.
- Исключение в `handle` скрывалось от очереди: ошибочная команда получала статус
  `done`. Исключение теперь передаётся очереди; она фиксирует `failed` и уведомляет
  пользователя, не повторяя возможный побочный эффект автоматически.
- Уведомления об истечении семи дней обработки направлялись основным согласующим.
  Теперь уведомляется команда соответствующего пространства.
- `SimpleQueryResult.success=false` при HTTP 200 ошибочно считался успехом.
  Такой ответ теперь вызывает ошибку; учёт кнопок и удаляемых сообщений сохраняется
  для последующих попыток.
- Словарь блокировок отправки сохранял записи для всех старых сообщений.
  Используются слабые ссылки: завершённые блокировки освобождаются, ожидающие
  отправки одному получателю остаются последовательными.

Ранее исправленные ошибки:

| Приоритет | Проблема | Исправление |
| --- | --- | --- |
| Высокий | Следующий запрос `/updates` подтверждал предыдущие события через `marker`, хотя их файлы ещё скачивались. Перезапуск в этот момент мог потерять материал. | Теперь входящие медиа сохраняются в SQLite до передачи следующего marker. Отдельный обработчик выполняет скачивание и генерацию с повторными попытками; остальные события обрабатываются до подтверждения пакета. |
| Высокий | После частичной публикации можно было изменить текст. В MAX и Telegram могли появиться разные варианты одного поста. | Правка и повторная генерация запрещены после успешной отправки хотя бы в один канал, а также при неопределённом результате отправки. Завершить публикацию исходного варианта по-прежнему можно. |
| Высокий | Между нажатием «Опубликовать» и началом отправки другой проверяющий мог изменить черновик. Старая кнопка публиковала новый несогласованный текст. | Версия черновика повторно проверяется после захвата права на публикацию. Устаревшее подтверждение отклоняется. |
| Средний | Ответ нейросети не проверялся по длине; ручная проверка не учитывала длину эмодзи при отправке в Telegram. | Генерация и ручная правка ограничены 3900 единицами UTF-16 или меньшим `MAX_POST_CHARS`. Это консервативный общий предел для двух платформ; схема MAX задаёт максимум 4000 символов. |
| Низкий | Обработчик требовал `callback.payload`, хотя в официальной схеме поле необязательное. | Callback без payload подтверждается без попытки выполнить команду и без сообщения об ошибке. |

## Проверенные контракты

| Операция | Результат сверки |
| --- | --- |
| Авторизация | Токен передаётся в заголовке `Authorization`, базовый адрес — `https://platform-api.max.ru`. |
| Получение событий | `GET /updates`, timeout 30, limit 100, список types через запятую соответствуют схеме. Особенности marker учтены исправлением выше. |
| Отправка | `POST /messages`, числовые `user_id`/`chat_id`, text и массив attachments. При публикации в канал `notify=false` не передаётся — схема запрещает этот режим для каналов. |
| Фото | `POST /uploads?type=image`, multipart-поле `data`; извлечение токена из `photos` совпадает с реализацией официального Python SDK. |
| Видео | `POST /uploads?type=video`, multipart `data`; используется токен загрузки. Повтор отправки предусмотрен для `attachment.not.ready`. |
| Скачивание видео | `GET /videos/{videoToken}` и прямой MP4 из `urls`. Ссылка просмотра из входящего вложения не используется как файл. |
| Кнопки | Вложение `inline_keyboard`, кнопки callback, ответ через `POST /answers?callback_id=…`. |
| Правка и удаление | `PUT /messages` и `DELETE /messages` возвращают `SimpleQueryResult`; проверяется не только HTTP-статус, но и поле `success`. |
| Альбомы | Отправляется массив image/video в исходном порядке. Лимит 10 — ограничение приложения для совместимости с Telegram. Реальное отображение смешанных наборов требует проверки в клиенте MAX. |

## Оставшиеся ограничения

1. **Long polling не рекомендован MAX для production.** Схема прямо указывает:
   “this method is not suitable for production environments”. Для постоянной
   эксплуатации следует добавить webhook, HTTPS-адрес, проверку секрета и
   надёжное сохранение входящих событий до ответа серверу MAX. В этом изменении
   webhook не добавлен; инструкция установки описывает существующий polling.
2. **Очередь покрывает фото, видео и альбомы.** Добавлены сохранение события до
   подтверждения marker, дедупликация по ID сообщения, связь с единственным
   черновиком, восстановление после перезапуска, кеш скачанных оригиналов и до
   8 попыток обработки. При аварии между отправкой проверяющему и записью результата
   может повториться сообщение согласования для того же черновика. Команды и
   callback также сохраняются в SQLite; выполняется до четырёх пользователей
   параллельно, по одной команде на человека. Ожидание ручного ввода хранится в
   памяти: после перезапуска нужно снова открыть правку или настройку. Если ссылка
   MAX истекла до первого скачивания, потребуется повторная отправка материала.
3. **Обработка новых материалов вынесена из polling.** Очередь последовательно
   обрабатывает медиа, а polling продолжает получать нажатия кнопок. Однако
   генерация по кнопке и публикация вынесены в отдельную очередь команд и не
   блокируют получение следующего пакета. Новые материалы обрабатывает один
   общий работник: большой ролик может задержать генерацию следующего материала
   другой команды. Команды одного пользователя также выполняются последовательно.
4. **Публикация в два сервиса не является атомарной.** При сетевом таймауте нельзя
   достоверно установить, создано ли сообщение. Бот сохраняет неопределённый
   результат и просит проверяющего проверить канал перед повтором. Добавлены
   статус по каждому каналу и подтверждение «пост уже есть» без повторной отправки.

## Проверка

Повторная проверка 5 ноября 2026 года: **350 тестов прошли**. Добавлены проверки
быстрой пары «кнопка → текстовый ответ» через настоящую очередь команд,
изоляции уведомлений об истечении срока, группового `/menu`, фиксации ошибки
обработчика, отказа API с HTTP 200, освобождения блокировок и сохранения
последовательности одновременных отправок. Проверка компиляции Python и
`git diff --check` также прошли. Реальные MAX/Telegram API не вызывались.

В исходном аудите прошли **233 теста**, включая 13 новых проверок.
11 новых проверок отдельно запущены на предыдущем коммите `9452ae1` и воспроизводят
ошибки; после исправлений они проходят. Остальные две проверяют порядок marker
и ограничение параллельной обработки. HTTP API в тестах заменён имитацией;
обработка видео проверяется также настоящим ffmpeg.

После добавления очереди, статусов, причин отклонения, списка ожидающих постов и
предупреждений об удалении **270 тестов прошли**. Новые тесты проверяют сохранение
события до marker через отдельное
соединение SQLite, восстановление после сбоя, повторную доставку готового черновика,
очистку кеша, ограничения доступа и отказоустойчивые сценарии согласования.
Отдельно проверены импорт набора файлов Docker и миграция старой базы с сохранением черновика.

После получения токена нужны проверки на тестовых каналах: одно фото, одно видео,
смешанный альбом, длинный текст, все действия проверяющего, права публикации,
повтор после отказа одного канала и перезапуск во время обработки файла.
