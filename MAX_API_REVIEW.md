# Проверка совместимости с MAX

Дата: 4 ноября 2026 года. Проверены адаптер MAX, обработка медиа, согласование,
публикация в два канала и связанные тесты. Это проверка кода и контрактов API;
отправка сообщений в настоящий MAX не выполнялась: токен пока не предоставлен.

## Официальные источники

- [OpenAPI MAX, проверенная версия](https://github.com/max-messenger/api-schema/blob/1a4a502fab096aa3a15d83d7ea95667ffb44d2ac/schema.yaml).
- [Официальный Python SDK, проверенная версия](https://github.com/max-messenger/max-botapi-python/tree/4a286baa06d38f2db9f7244d94f89508743f8fee).
- [Документация Bot API](https://dev.max.ru/docs-api/).

Сайт dev.max.ru недоступен из среды проверки (HTTP 403), поэтому источником
сверки служит официальная схема из организации max-messenger на GitHub.
Репозиторий схемы обновлён перед проверкой. Возможные расхождения работающего
сервиса со схемой нужно проверять после получения токена.

## Найденные и исправленные ошибки

| Приоритет | Проблема | Исправление |
| --- | --- | --- |
| Высокий | Следующий запрос `/updates` подтверждал предыдущие события через `marker`, хотя их файлы ещё скачивались. Перезапуск в этот момент мог потерять материал. | Следующий marker передаётся после завершения обработки пакета. Обработчики, включая скачивание, учитываются при штатном завершении. Одновременно обрабатываются до двух событий. |
| Высокий | После частичной публикации можно было изменить текст. В MAX и Telegram могли появиться разные варианты одного поста. | Правка и повторная генерация запрещены после успешной отправки хотя бы в один канал, а также при неопределённом результате отправки. Завершить публикацию исходного варианта по-прежнему можно. |
| Высокий | Между нажатием «Опубликовать» и началом отправки другой проверяющий мог изменить черновик. Старая кнопка публиковала новый несогласованный текст. | Версия черновика повторно проверяется после захвата права на публикацию. Устаревшее подтверждение отклоняется. |
| Средний | Ответ нейросети не проверялся по длине; ручная проверка не учитывала длину эмодзи при отправке в Telegram. | Генерация и ручная правка ограничены 3900 единицами UTF-16 или меньшим `MAX_POST_CHARS`. Это консервативный общий предел для двух платформ; схема MAX задаёт максимум 4000 символов. |
| Низкий | Обработчик требовал `callback.payload`, хотя в официальной схеме поле необязательное. | Callback без payload подтверждается без попытки выполнить команду и без сообщения об ошибке. |

## Проверенные контракты

| Операция | Результат сверки |
| --- | --- |
| Авторизация | Токен передаётся в заголовке `Authorization`, базовый адрес — `https://platform-api.max.ru`. |
| Получение событий | `GET /updates`, timeout 30, limit 100, список types через запятую соответствуют схеме. Особенности marker учтены исправлением выше. |
| Отправка | `POST /messages`, числовые `user_id`/`chat_id`, text и массив attachments. При публикации в канал `notify=false` не передаётся — схема запрещает этот режим для каналов. |
| Фото | `POST /uploads?type=image`, multipart-поле `data`; извлечение токена из `photos` совпадает с реализацией официального Python SDK. |
| Видео | `POST /uploads?type=video`, multipart `data`; используется токен загрузки. Повтор отправки предусмотрен для `attachment.not.ready`. |
| Скачивание видео | `GET /videos/{videoToken}` и прямой MP4 из `urls`. Ссылка просмотра из входящего вложения не используется как файл. |
| Кнопки | Вложение `inline_keyboard`, кнопки callback, ответ через `POST /answers?callback_id=…`. |
| Альбомы | Отправляется массив image/video в исходном порядке. Лимит 10 — ограничение приложения для совместимости с Telegram. Реальное отображение смешанных наборов требует проверки в клиенте MAX. |

## Оставшиеся ограничения

1. **Long polling не рекомендован MAX для production.** Схема прямо указывает:
   “this method is not suitable for production environments”. Для постоянной
   эксплуатации следует добавить webhook, HTTPS-адрес, проверку секрета и
   надёжное сохранение входящих событий до ответа серверу MAX. В этом изменении
   webhook не добавлен; инструкция установки описывает существующий polling.
2. **Нет постоянной очереди и дедупликации входящих событий.** После аварийного
   завершения между обработкой события и подтверждением marker возможна его
   повторная доставка и повторное создание черновика. Исправление marker снижает
   риск потери при перезапуске, но не обеспечивает обработку «ровно один раз».
   Ошибки обработки логируются и могут завершать обработку события без
   автоматического повтора. Следующий этап — очередь в БД с уникальным ID события,
   состоянием обработки и повторными попытками.
3. **Долгие видео задерживают следующие события.** Ограничение параллелизма
   защищает память, но следующий пакет событий ожидает завершения текущего.
   При нагрузке нажатия кнопок могут обрабатываться с задержкой. Постоянная
   очередь с отдельными обработчиками медиа устранит эту зависимость.
4. **Публикация в два сервиса не является атомарной.** При сетевом таймауте нельзя
   достоверно установить, создано ли сообщение. Бот сохраняет неопределённый
   результат и просит проверяющего проверить канал перед повтором.

## Проверка

Полный набор: **233 теста прошли**, включая 13 новых проверок этого аудита.
11 новых проверок отдельно запущены на предыдущем коммите `9452ae1` и воспроизводят
ошибки; после исправлений они проходят. Остальные две проверяют порядок marker
и ограничение параллельной обработки. HTTP API в тестах заменён имитацией;
обработка видео проверяется также настоящим ffmpeg.

После получения токена нужны проверки на тестовых каналах: одно фото, одно видео,
смешанный альбом, длинный текст, все действия проверяющего, права публикации,
повтор после отказа одного канала и перезапуск во время обработки файла.
