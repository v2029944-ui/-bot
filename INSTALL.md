# Установка на VPS: MAX → согласование → MAX и Telegram

Инструкция для Ubuntu 24.04 LTS или 22.04 LTS и Docker Compose.
Участник сам редактирует и публикует свои посты в MAX. Telegram только публикует результат.
Администратор пространства управляет людьми, настройками и всеми постами команды.
Старые роли сотрудника и проверяющего автоматически объединяются в участника;
администраторы и владельцы сохраняют права. Обновление не требует новых переменных .env.

Для запуска необходим токен MAX. Для работающей установки используйте раздел
[Обновление кнопкой в MAX](#обновление-кнопкой-в-max) или обновление из ZIP; переустановка не нужна.

## Кто выполняет команды

| Где и под кем | Для чего |
| --- | --- |
| На вашем компьютере | Подключение по SSH и отправка ZIP на сервер |
| На сервере под `root` | Однократная установка Docker и создание пользователя `bot` |
| На сервере под `bot` | Настройки, запуск, обновление и просмотр логов |
| В чате MAX, под администратором бота | Меню, пользователи, согласование, кнопка обновления |

`bot` — имя пользователя **Linux на сервере**. Оно не связано с аккаунтом в MAX или Telegram.
После настройки Docker все команды `docker compose` ниже выполняются под `bot`, **без `sudo`**, из `/home/bot/post_bot`.
Для резервной копии файлов, созданных контейнером, отдельно указан `sudo`.

Проверить текущего пользователя и папку можно командами `whoami` и `pwd`.
В примерах замените `IP_СЕРВЕРА` своим адресом. Не вводите этот текст буквально.

## 1. Что подготовить

- VPS с Ubuntu, доступ по SSH. Для обработки видео разумная отправная точка — 2 CPU, 4 ГБ RAM и 20 ГБ диска; потребность в диске зависит от числа материалов.
- Токен MAX: [инструкция по созданию бота](https://dev.max.ru/help/chatbots/), [кабинет MAX](https://dev.max.ru/ui/).
- Числовые ID канала MAX, администратора и участников. ID MAX отличаются от Telegram ID. Способ получения смотрите в [официальной документации](https://dev.max.ru/docs-api/) и [официальном примере получения ID](https://github.com/max-messenger/max-botapi-python/tree/main/examples/get_ids). Не публикуйте события с личными данными или токены в открытом доступе.
- Токен Telegram от `@BotFather` и адрес канала, например `@company_news`.
- Доступ ботов к каналам с правом публикации.
- Ключ нейросети, адрес её API и название модели с поддержкой изображений, если оставляете `LLM_VISION=1`.

Остановите другие запуски **того же MAX-бота** перед включением этого экземпляра. Здесь используется long polling; если ранее подключали webhook, его нужно отключить согласно документации MAX. Telegram входящие сообщения не опрашивает.

Официальная спецификация MAX не рекомендует long polling для production и предлагает webhook. Текущая версия webhook ещё не поддерживает. Перед постоянной эксплуатацией ознакомьтесь с [устройством очередей и ограничениями](ARCHITECTURE.md#ограничения).

Серверу нужен исходящий HTTPS-доступ к GitHub, реестрам зависимостей, API нейросети, `api.telegram.org`, `platform-api2.max.ru` и адресам загрузки/скачивания файлов, которые возвращает MAX. Доступность MAX с конкретного VPS проверяется при запуске.

## 2. Подключение и пользователь bot

**На вашем компьютере**, в Терминале или PowerShell:

```sh
ssh root@IP_СЕРВЕРА
```

При первом подключении проверьте отпечаток SSH-ключа по данным провайдера. Пароль при вводе не отображается.

**На сервере под `root`:**

```sh
apt update
apt upgrade -y
apt install -y ca-certificates curl unzip nano
adduser bot
usermod -aG sudo bot
```

Если `bot` уже существует, повторно выполнять `adduser bot` не нужно.

## 3. Установка Docker

**На сервере под `root`.** Для чистой Ubuntu установите Docker из официального APT-репозитория:

```sh
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
. /etc/os-release
cat > /etc/apt/sources.list.d/docker.sources <<EOF_DOCKER
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: ${UBUNTU_CODENAME:-$VERSION_CODENAME}
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF_DOCKER
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
usermod -aG docker bot
```

Если Docker уже установлен и работает, переустанавливать его не нужно. Проверка:

```sh
docker --version
docker compose version
```

Группа `docker` даёт широкие права управления сервером; добавляйте в неё только доверенных пользователей.
Официальная инструкция и разбор конфликтов со старыми пакетами: [Docker Engine для Ubuntu](https://docs.docker.com/engine/install/ubuntu/).

**Теперь выйдите из root:**

```sh
exit
```

**На вашем компьютере подключитесь заново уже под `bot`:**

```sh
ssh bot@IP_СЕРВЕРА
```

**На сервере под `bot`:**

```sh
whoami
id -nG
docker ps
```

Ожидается имя `bot`, группа `docker` в списке и отсутствие ошибки доступа. Новый вход по SSH нужен, чтобы членство в группе вступило в силу.

## 4. Загрузка кода

**На вашем компьютере:** скачайте [ZIP ветки main](https://github.com/v2029944-ui/-bot/archive/refs/heads/main.zip). Для закрытого репозитория войдите в GitHub. Сохраните архив под именем `post_bot.zip`.

В отдельном терминале **на компьютере**, из папки со скачанным архивом:

```sh
scp post_bot.zip bot@IP_СЕРВЕРА:~/post_bot.zip
```

Можно также загрузить файл через SFTP-клиент под пользователем `bot` в `/home/bot/`.

**На сервере под `bot` — для первой установки:**

```sh
unzip -t ~/post_bot.zip
stage=$(mktemp -d "$HOME/post_bot-install.XXXXXX")
unzip -q ~/post_bot.zip -d "$stage"
mkdir -p ~/post_bot
cp -a "$stage/-bot-main/." ~/post_bot/
cd ~/post_bot
ls Dockerfile docker-compose.yml env.example main.py
```

В ZIP с GitHub папка называется `-bot-main`.
При ошибке распаковки или копирования сначала устраните её; не продолжайте запуск с неполным набором файлов.

## 5. Настройки .env

**На сервере под `bot`, в `~/post_bot`:**

```sh
cd ~/post_bot
cp -n env.example .env
chmod 600 .env
nano .env
```

`cp -n` сохраняет уже существующий `.env`. Не заменяйте рабочий файл настроек целиком новым образцом.
Заполните строки своими значениями; приведённые ниже обозначения не являются рабочими токенами:

```dotenv
TG_TOKEN=ВАШ_ТОКЕН_TELEGRAM
TG_CHANNEL=@ВАШ_КАНАЛ_TELEGRAM

MAX_TOKEN=ВАШ_ТОКЕН_MAX
MAX_CHANNEL=ЧИСЛОВОЙ_ID_КАНАЛА_MAX
MAX_APPROVERS=
MAX_ADMINS=ВАШ_ЧИСЛОВОЙ_ID_MAX
MAX_EMPLOYEES=ID_СОТРУДНИКА_1,ID_СОТРУДНИКА_2
APPROVAL_PLATFORM=max

LLM_PROVIDER=openai
LLM_API_KEY=ВАШ_КЛЮЧ_НЕЙРОСЕТИ
LLM_BASE_URL=https://api.aitunnel.ru/v1
MODEL=gpt-4.1-mini
LLM_VISION=1
COMPANY=Название компании

GITHUB_REPO=
GITHUB_BRANCH=main
```

- Адрес AITunnel указан как пример. Если ключ от другого провайдера, укажите его адрес и доступную модель.
- `MAX_ADMINS` даёт административные права и право согласования. Для нескольких людей укажите ID через запятую.
- Добавлять людей можно и без изменения `.env`: в меню MAX откройте «Люди» → «➕ Добавить человека» и отправьте ID пользователя MAX. Он будет добавлен как участник. Это работает в основном и в отдельных пространствах. Администраторов назначайте в разделе «Люди».
- При `MAX_ADMINS` и `ACCESS_REQUESTS=1` незнакомые пользователи могут отправить заявку; администратор одобрит её в MAX. Уже известным участникам можно сразу прописать `MAX_EMPLOYEES`.
- Списки `MAX_EMPLOYEES` и прежний `MAX_APPROVERS` задают участников, `MAX_ADMINS` — администраторов. Если все три списка пусты, бот принимает материалы от любых пользователей; для закрытой команды задайте администратора и добавляйте участников через меню.
- Сначала оставьте `GITHUB_REPO` пустым: бот будет работать из собранного Docker-образа. Кнопку обновления можно настроить отдельно ниже.
- `MAX_LOG_UPDATES=0` оставьте выключенным для обычной работы.
- `EMPLOYEE_CONFIRM=text` включает короткое подтверждение приёма, `off` выключает. Подтверждение приходит сообщением в MAX.

В nano: `Ctrl+O`, Enter, затем `Ctrl+X`. Не отправляйте содержимое `.env` в чат и не загружайте его в GitHub.

## 6. Первый запуск

**На сервере под `bot`, в `~/post_bot`:**

```sh
cd ~/post_bot
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 bot
```

Сборка устанавливает Python-зависимости и ffmpeg для видео. Отдельно ставить Python и ffmpeg на VPS не требуется.
В `ps` контейнер должен оставаться запущенным, а в логах не должно быть повторяющихся ошибок запуска или авторизации. Один статус `Up` ещё не подтверждает правильную работу с каналами.

Для просмотра новых логов:

```sh
docker compose logs -f --tail 100 bot
```

`Ctrl+C` завершит просмотр логов, бот продолжит работать.

## 7. Проверка в MAX и Telegram

**В приложении MAX:**

1. Администратор и участники открывают чат с ботом и нажимают «Начать».
2. Администратор отправляет `/menu`; должны появиться кнопки управления, включая «👥 Люди», «📊 Статус», «🔄 Обновить».
3. Отправьте `/status`. Проверка нейросети выполняет реальный запрос к вашему провайдеру.
4. Участник отправляет фото, видео или выбирает до 10 фото и видео и отправляет одним сообщением с общей подписью. Автор получает весь набор и один черновик в MAX. Другим участникам он не рассылается.
5. Автор при необходимости редактирует текст, нажимает «✅ Опубликовать», затем «✅ Да, опубликовать». Первое нажатие только открывает подтверждение; «↩️ Отмена» оставляет пост на проверке.
6. Проверьте оба канала: MAX и Telegram. Затем повторите с коротким видео и смешанным альбомом из фото и видео.

Telegram не отвечает на `/start` и не показывает меню — это ожидаемо. Все рабочие действия выполняются в MAX.
Для альбома действует ограничение до 10 вложений и до 100 МиБ в сумме. Отдельные сообщения не объединяются автоматически. Для каждого видео по умолчанию действуют лимиты 49 МиБ и 180 секунд. Нейросеть получает подпись и кадры; речь не расшифровывается.
При неопределённом результате публикации сначала проверьте канал, затем подтверждайте повтор, чтобы избежать дубля.
Перед изменением каналов завершите частичные публикации. Если канал уже изменён,
бот блокирует продолжение отправки в другой канал: верните прежние настройки и
проверьте результат в них. Для ещё не начатой публикации откройте подтверждение
заново, чтобы подтвердить новые настройки.

## 8. Изменение настроек и повседневные команды

**Все команды — на сервере под `bot`, из `~/post_bot`.**

После правки `.env`:

```sh
cd ~/post_bot
docker compose up -d --force-recreate
```

Это перечитывает настройки, но **не скачивает новый код**. `docker compose restart` не перечитывает `.env`.

| Задача | Команда |
| --- | --- |
| Проверить состояние | `docker compose ps` |
| Последние логи | `docker compose logs --tail 100 bot` |
| Перезапустить без смены настроек | `docker compose restart bot` |
| Остановить | `docker compose stop bot` |
| Запустить после остановки | `docker compose start bot` |
| Пересобрать после обновления файлов | `docker compose up -d --build --force-recreate` |

Docker включён в автозапуск, а в Compose задано `restart: unless-stopped`. После перезагрузки сервера работавший контейнер запускается снова. Вручную остановленный контейнер нужно запустить самостоятельно.

## Резервная копия

**На сервере под `bot`, из `~/post_bot`.** Для полной согласованной копии базы, медиа и настроек остановите контейнер на время архивации:

```sh
cd ~/post_bot
mkdir -p ~/bot-backups
chmod 700 ~/bot-backups
docker compose stop bot
backup="$HOME/bot-backups/post_bot-$(date +%Y%m%d-%H%M%S).tar.gz"
sudo tar -czf "$backup" .env data
sudo chown bot:bot "$backup"
chmod 600 "$backup"
sudo tar -tzf "$backup" > /dev/null
docker compose start bot
```

Дождитесь успешного завершения архивации. Сохраните копию также вне VPS через SFTP.
Архив содержит ключи из `.env`, поэтому храните его как секретный файл.
Не удаляйте `data`: там базы пространств, правила, пользователи, черновики, незавершённые правки и медиа.

## Обновление вручную из ZIP

Этот способ предназначен для `GITHUB_REPO=` (пустое значение).

1. Сделайте резервную копию по разделу выше.
2. **На компьютере** скачайте свежий ZIP с GitHub и отправьте его на сервер командой `scp` из шага 4.
3. **На сервере под `bot`:**

```sh
cd ~/post_bot
unzip -t ~/post_bot.zip
stage=$(mktemp -d "$HOME/post_bot-update.XXXXXX")
unzip -q ~/post_bot.zip -d "$stage"
cp -a "$stage/-bot-main/." ~/post_bot/
docker compose up -d --build --force-recreate
docker compose logs --tail 100 bot
```

Папки `.env`/`data` в репозитории отсутствуют; копирование файлов из ZIP их сохраняет.
Существующий `env.example` обновится, ваш `.env` — нет. Новые обязательные параметры добавьте вручную перед запуском.

**Если `GITHUB_REPO` заполнен, простая пересборка образа может оставить старый код из `./code`.**
Либо используйте кнопку обновления, либо для перехода на ручной способ очистите значение `GITHUB_REPO` в `.env` и выполните пересборку с `--force-recreate`. Папку `code` удалять не нужно.

## Обновление кнопкой в MAX

**На сервере под `bot`, в `~/post_bot`:** откройте `nano .env` и задайте:

```dotenv
GITHUB_REPO=https://github.com/v2029944-ui/-bot.git
GITHUB_BRANCH=main
```

Это URL для репозитория, доступного без авторизации. Если репозиторий закрытый, серверу нужны права чтения GitHub. Авторизация вашей браузерной сессии и облачной среды на VPS не переносится. До настройки доступа используйте ручное обновление из ZIP. Поддерживаемый текущим загрузчиком вариант — HTTPS URL с токеном чтения, сохранённый только в защищённом `.env`; не вставляйте токен в команды терминала или сообщения.

Если `./code` уже существует от прошлой установки, контейнер использует именно его и не скачает новую версию автоматически при пересоздании. Перед **первым включением или повторным включением** этого способа сохраните прежнюю папку:

```sh
cd ~/post_bot
docker compose stop bot
if [ -d code ]; then
  sudo mv code "code-before-github-$(date +%Y%m%d-%H%M%S)"
fi
docker compose up -d --build --force-recreate
docker compose logs --tail 100 bot
```

После успешного первого запуска код находится в новой папке `./code`.
Дальше **в MAX под аккаунтом из `MAX_ADMINS`**: `/menu` → «🔄 Обновить» → действие обновления.
Папку `code` при обычных обновлениях переименовывать не нужно.

Бот скачивает код из GitHub, устанавливает изменившиеся зависимости для проверки, запускает тесты и переключается на новую версию. При сбое проверки остаётся прежняя версия. Для неудачного запуска после переключения предусмотрен откат. Это не заменяет резервную копию данных.

Кнопка не меняет ваш `.env`, Dockerfile и Compose на сервере. Если обновление требует новых настроек или изменений Docker, примените их вручную. Не правьте код внутри `./code`: при обновлении он заменяется версией из GitHub.

## Переход на API2 MAX

Текущая версия использует `https://platform-api2.max.ru`, как указано в
[официальной документации MAX](https://github.com/max-messenger/api-schema/blob/main/README.mdx#базовый-url).
Корневой сертификат Минцифры включён в `certs/`; бот проверяет его отпечаток
и добавляет только в HTTPS-клиент MAX. Цепочка сертификатов и имя сервера
проверяются. Ставить сертификат в ОС VPS или добавлять новые настройки `.env`
не требуется. [Источник и отпечаток сертификата](certs/README.md).

При уже настроенном обновлении через GitHub этот переход доставляется обычной
кнопкой: вместе с Python-кодом скачиваются `max_tls.py` и `certs/`.
Если ещё не применена пересборка после полного аудита, выполните также следующий
временный раздел. При установке из ZIP перенесите **весь** архив, включая `certs`,
и пересоберите образ по разделу ручного обновления.

Если бот не отвечает и нажать кнопку невозможно, при настроенном `GITHUB_REPO`
и существующей папке `code` запустите штатную проверку обновления через Docker.
**Под Linux-пользователем `bot`, в `/home/bot/post_bot`:**

```sh
cd /home/bot/post_bot
docker compose stop bot
docker compose run --rm -T --no-deps --entrypoint python bot /app/updater.py
```

Проверьте вывод загрузчика. Продолжайте только при `[updater] ok` или `nochange`.
При `failed`/`tests_failed` сначала устраните указанную причину.
Если пересборка после полного аудита ещё не выполнена, **оставьте бот остановленным**
и продолжите с шага 2 следующего раздела. Если образ уже пересобран, запустите бот:

```sh
docker compose start bot
docker compose logs --tail 100 bot
```

Отдельный контейнер выполняет только обновление с тестами и не запускает второй
polling-процесс. После запуска проверьте `/menu` и один материал в тестовых группах.
При ошибке TLS проверьте наличие файлов новой версии и сетевой доступ к API2;
не отключайте проверку сертификатов.

## Временно: пересборка после обновления кнопкой

Этот раздел применяет весь набор исправлений аудита: новый `entrypoint.sh`,
загрузчик обновлений, lock-файлы зависимостей и изменённый Dockerfile.
**Одной кнопки для полного применения этого выпуска недостаточно.**
После подтверждения успешной установки раздел можно удалить.

Результаты репетиции перехода со старых версий: [проверка перед обновлением](PREUPDATE_CHECK.md).
Для первого обновления рекомендуется следующий порядок: остановить бот, скачать
и проверить новый код отдельным контейнером, пересобрать образ и только затем
запустить бот. Так новый код впервые запустится уже с новым загрузчиком.
Если кнопку уже нажимали, этот порядок тоже подходит: повторная проверка покажет
`nochange`, когда в `code` уже находится текущая версия.

Сначала завершите частичные публикации и проверьте публикации с неизвестным
результатом в каналах. Не меняйте каналы во время перехода. Сделайте резервную
копию `.env` и всей папки `data` по разделу выше; убедитесь, что архив проверен.

**1. На сервере под Linux-пользователем `bot`:**

Если вошли как `root`, сначала выполните `su - bot`. Все следующие команды
выполняйте под `bot`, без `sudo`, в `/home/bot/post_bot`.
Этот порядок предназначен для уже настроенного `GITHUB_REPO` и существующей
папки `code`. Для установки без GitHub используйте обновление из ZIP.

```sh
whoami
cd /home/bot/post_bot
ls -ld code/.git
docker compose stop bot
docker compose run --rm -T --no-deps --entrypoint python bot /app/updater.py
```

`whoami` должен показать `bot`. Продолжайте только после `[updater] ok` или
`[updater] nochange`. Загрузчик может завершить команду без ошибки даже при
неудаче проверки: одного кода завершения команды недостаточно.
При `failed`, `tests_failed` или другом сообщении остановитесь и устраните причину.
Не запускайте бот между скачиванием кода и пересборкой образа. Отдельный контейнер
выполняет загрузчик с тестами, без запуска второго polling-процесса.

**2. В той же папке, под `bot`:** проверьте файлы нового выпуска.

```sh
ls code/entrypoint.sh code/requirements-dev.lock code/compatibility.json code/max_tls.py code/certs/russian_trusted_root_ca.crt
```

При ошибке любой команды остановитесь и устраните её; не выполняйте следующие
шаги с неполным набором файлов.

**3. В той же папке, под `bot`:** перенесите все отслеживаемые исходники из
обновлённой папки `code` в папку сборки. Команды сами создают архив и копируют
его содержимое; открывать и переносить файлы вручную не нужно.

```sh
stage=$(mktemp -d "$HOME/post_bot-rebuild.XXXXXX")
cp entrypoint.sh "$stage/entrypoint.sh.old"
cp Dockerfile "$stage/Dockerfile.old"
docker compose run --rm -T --no-deps --entrypoint git bot -C /app/code archive --format=tar HEAD > "$stage/source.tar"
tar -tf "$stage/source.tar" > /dev/null
tar -xf "$stage/source.tar" -C /home/bot/post_bot
sh -n entrypoint.sh
```

Git запускается внутри отдельного контейнера из прежнего образа, где он уже
установлен; отдельно ставить Git на VPS не нужно. Основной бот остаётся остановленным.
Docker-команду выполняет пользователь `bot`.
Архив содержит только файлы Git: `.env`, `data` и сама рабочая папка `code` в него
не входят и сохраняются. Это важно: простого копирования одного `entrypoint.sh`
для этого выпуска недостаточно — Docker должен получить также новые модули,
загрузчик, описание совместимости, lock-файлы и каталог `certs`.

**4. Под `bot`, в `/home/bot/post_bot`:**

```sh
docker compose build bot
```

При ошибке сборки оставьте бот остановленным и устраните причину; не запускайте
новый код в прежнем образе. Дождитесь успешной сборки, затем:

```sh
docker compose up -d --force-recreate bot
docker compose ps
docker compose logs --tail 100 bot
```

Проверьте в MAX меню, список людей, один материал и публикацию в тестовые группы.
При первом переходе и откате к старой модели ролей прежние назначения могут
потребовать повторного добавления; это принято для данной установки. Главные
администраторы из `MAX_ADMINS` сохраняются в `.env`.
Последующие обновления проверяют совместимость формата данных для обновления
и отката, а библиотеки устанавливают из одного lock-файла с хешами.
Если pip завершился с ошибкой, новый код не запускается поверх частично
обновлённого окружения: сначала выполняется предусмотренный откат либо бот
завершается с ошибкой для диагностики.

Для последующих обычных обновлений Python-кода достаточно кнопки. Будущие
изменения Dockerfile или скрипта внутри образа снова требуют пересборки.

## Если возникла ошибка

| Сообщение или поведение | Что проверить |
| --- | --- |
| `permission denied` при Docker | Под `bot` выполните `id -nG`. Если группы `docker` нет, под `root` выполните `usermod -aG docker bot`, затем заново подключитесь по SSH как `bot`. Не меняйте права Docker-сокета на общедоступные. |
| `no configuration file provided` | Под `bot` выполните `cd ~/post_bot`; там должен быть `docker-compose.yml`. |
| Нужен `MAX_TOKEN` | Укажите токен MAX в `.env` и пересоздайте контейнер. Без него бот не работает. |
| MAX отклонил токен, 401/403 | Проверьте токен и права бота по документации MAX; после правки `.env` выполните пересоздание. |
| Бот не присылает черновик автору | Автор должен открыть чат с ботом в MAX; проверьте его доступ и режим уведомлений. Администратор может открыть пост через «На проверке». |
| Telegram не публикует | Проверьте `TG_TOKEN`, `TG_CHANNEL` и право бота публиковать в канале. |
| Ошибка нейросети | Проверьте соответствие ключа адресу `LLM_BASE_URL`, доступность модели `MODEL` и баланс провайдера. |
| Кнопка обновления не работает | Нужны `MAX_ADMINS`, заполненный `GITHUB_REPO`, доступ VPS к GitHub и запуск через штатный entrypoint. |
| После пересборки остаётся старый код | При заполненном `GITHUB_REPO` код берётся из `./code`; используйте соответствующий раздел обновления. |
| Видео не принимается | Проверьте размер, длительность и наличие подписи. После установки новых зависимостей выполните пересборку или штатное обновление. |

Для диагностики под `bot` в `~/post_bot` выполните `docker compose logs --tail 100 bot`.
Перед передачей лога уберите токены, ключи и личные данные. Не присылайте `.env` целиком.

## Хранение фото и видео

Для нескольких независимых команд доступна настройка [рабочих пространств](SPACES.md).
Главный администратор создаёт их из MAX, без установки отдельных контейнеров.
Все базы и медиа пространств находятся внутри существующего Docker-тома `data`;
при резервном копировании включайте его целиком.

После успешной публикации во всех подключённых каналах бот удаляет локальные фото,
видео, превью, текст поста, исходную подпись, данные автора и подробные отметки по
каналам. Посты в MAX и Telegram остаются. В базе сохраняются ID черновика, ключ
исходного сообщения, статус «опубликован», платформа и дата для статистики и защиты
от дублей. Пока публикация не завершена, текст, файлы и результаты отправки по
каналам сохраняются для повторной попытки.

Опубликованные тексты больше не используются как примеры для нейросети; отдельно
сохранённые правила редакции продолжают работать. Содержимое опубликованных
записей очищается автоматически при запуске обновлённого бота. Менять `.env` для
этого не требуется. Эта очистка касается рабочей базы, а не ранее созданных резервных копий.

Необработанные черновики хранятся по умолчанию 7 дней с последней отправки на согласование (или с создания, если ещё не отправлялись). Затем они закрываются, а файлы удаляются при очередной очистке: при запуске и каждые 6 часов. При обновлении также очищаются оставшиеся файлы уже опубликованных постов.

У отклонённых и истёкших черновиков текст, причина и данные автора хранятся
ещё 7 дней после закрытия, затем очищаются при уборке. Файлы удаляются сразу.
Большие очереди очистки обрабатываются порциями, с продолжением в следующих
циклах обслуживания.

Незавершённые публикации, у которых хотя бы один канал уже получил пост или результат
отправки неизвестен, автоматически по сроку не удаляются. Завершите их через
«На проверке», предварительно проверив каналы.

В течение последних суток перед удалением работающий бот предупреждает авторов.
Предупреждение не меняет срок хранения. Если бот был выключен, просроченные материалы
могут быть удалены при запуске без предварительного сообщения.

Новые входящие материалы проходят постоянную очередь в той же базе `data/drafts.db`.
Временные оригиналы для повторной обработки сохраняются в `data/inbox` максимум на
7 дней с приёма; при успешной обработке удаляются раньше. Каталог `data` уже подключён
как постоянный том Docker. Не удаляйте его при обновлении. В меню администратора
«Обработка материалов» видны ошибки и доступна повторная обработка.

Срок хранения задаётся `DRAFT_TTL_DAYS`, по умолчанию 7. Изменение `.env`
применяется пересозданием контейнера под `bot`, из `~/post_bot`:
`docker compose up -d --force-recreate`. Истёкшие материалы очищаются при запуске
и очередной уборке. Webhook пока не используется —
[объяснение HTTPS, домена и расходов](WEBHOOK.md).

## Параллельная обработка и правки

Незавершённые ручные правки, комментарии, причины отклонения, ввод правил и настройки
ссылки сохраняются в SQLite до 7 дней. После перезапуска продолжайте ввод; `/cancel`
отменяет его. Уже изменённый администратором вариант защищён проверкой версии.

По умолчанию `MATERIAL_WORKERS=2`: одновременно готовятся материалы двух разных
пространств. В одном пространстве обрабатывается по одному материалу. Тяжёлая
обработка медиа общая и последовательная; запросов нейросети не больше трёх одновременно.
На VPS с ограниченными ресурсами можно указать `MATERIAL_WORKERS=1` в `.env` и
выполнить под `bot`, из `~/post_bot`, `docker compose up -d --force-recreate`.
Добавлять этот параметр необязательно: при его отсутствии используется 2.

Изменение структуры Python-модулей применяется обычной кнопкой обновления GitHub.
Для ручного обновления копируйте весь ZIP, включая каталог `services`.

Изменения Python-кода получает штатная кнопка обновления. Изменения `entrypoint.sh`
или `Dockerfile` требуют пересборки Docker-образа из обновлённых файлов и пересоздания
контейнера: они не подменяются обновлением папки `code`. Это относится и к исправлению
повторной установки зависимостей после неудачной установки и отката.
