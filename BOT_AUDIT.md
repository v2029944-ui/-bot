# Проверка бота — 5 ноября 2026

Проверена текущая рабочая копия с новой моделью ролей. Проверка не устанавливает
обновление на VPS и не заменяет проверку настоящих ботов в каналах.

## Источники MAX

Сайт dev.max.ru/docs-api из облачной среды ответил HTTP 403. Для сверки использованы
официальные репозитории, полученные через HTTPS Git с проверкой TLS:

- [Схема API](https://github.com/max-messenger/api-schema/blob/1a4a502fab096aa3a15d83d7ea95667ffb44d2ac/schema.yaml), commit `1a4a502fab096aa3a15d83d7ea95667ffb44d2ac`.
- [Python SDK](https://github.com/max-messenger/max-botapi-python/tree/4a286baa06d38f2db9f7244d94f89508743f8fee), commit `4a286baa06d38f2db9f7244d94f89508743f8fee`.

| Проверено | Результат по схеме и коду |
| --- | --- |
| Авторизация | Токен передаётся в заголовке Authorization |
| GET /updates | timeout=30, limit=100, фильтры types; marker подтверждается после сохранения событий |

Это сверка контракта, а не успешные запросы к API с рабочими токенами.

## Исправлено

1. **Права главного администратора.** Раньше назначение администратора через меню
   основного пространства делало его главным: открывало создание пространств и
   обновление общего процесса. Теперь эти полномочия проверяются по исходному
   списку MAX_ADMINS. Добавлены проверки меню, старых кнопок, прямого запуска
   обновления и доступа к пространствам. Права администратора своей команды сохранены.
2. **Слишком частый polling.** При мгновенных ответах MAX цикл мог опрашивать сервер
   без паузы. Введён минимальный интервал 300 мс с учётом времени запроса и обработки.
   Длинные запросы не получают лишней паузы. Подтверждение marker и постоянные очереди сохранены.
3. **Блокировки загрузки.** Существовала периодическая очистка, поэтому постоянная
   утечка не установлена. Однако очистка по locked() могла удалить блокировку между
   освобождением и захватом ожидающей задачей. WeakValueDictionary сохраняет блокировку,
   пока её используют/ожидают, и освобождает после использования без обхода словаря.

## Ограничения и следующие улучшения

- MAX официально рекомендует webhook и считает long polling неподходящим для
  production из-за ограничений скорости и срока хранения событий. Бот пока
  использует long polling; переход на webhook требует отдельной реализации,
  HTTPS endpoint и проверки развёртывания. См. WEBHOOK.md.
- Без рабочих токенов и VPS не проверены права настоящих каналов, внешний вид
  медиа/кнопок в приложении MAX, загрузка файлов через реальные CDN и нагрузка сервера.
- Нет оснований утверждать, что перечисленные исправления уже опубликованы на GitHub
  или установлены на сервере пользователя.

## Дополнительная проверка оставшихся участков

Дополнительно просмотрены хранение, очистка, медиаконвертация, отмена потоковых
заданий, расписания, генерация/сравнение моделей, формирование ссылок, запуск
контейнера и обновление с откатом. Найдены и исправлены ещё четыре проблемы:

1. Очистка по DRAFT_TTL_DAYS могла удалить незавершённую публикацию с успешной
   или неопределённой отправкой в канал. Такие записи теперь сохраняются до
   решения человека; предупреждение об автоматическом удалении им не отправляется.
2. В ночном окне (например, пн–пт 20–06) часы после полуночи ошибочно относились
   к новому дню. Теперь смена пятницы продолжается в субботу до 06:00, а раннее
   утро понедельника не считается частью ещё не начавшейся смены понедельника.
3. Отмена await asyncio.to_thread освобождала ограничение тяжёлой обработки,
   хотя поток ещё продолжал работать. Лимит теперь удерживается до завершения
   потока. Созданные им после отмены файлы удаляются обратным вызовом, пока процесс
   продолжает работать. Принудительное завершение всего процесса не позволяет
   гарантировать выполнение обратных вызовов; файлы-сироты убирает housekeeping.
4. После частичного сбоя pip оставалась старая отметка requirements, из-за чего
   откат мог пропустить восстановление прежних библиотек. При ошибке установки
   отметка удаляется; следующий запуск сверяет и устанавливает нужные зависимости.
   Установка библиотек остаётся нетранзакционной: наличие сети и успешный pip
   по-прежнему необходимы для восстановления зависимостей.

Итоговый полный прогон: **408 тестов прошли**. В том числе проверены отложенная
отмена настоящего потока, удаление созданного после отмены файла, ночные границы

Компиляция Python, синтаксис shell и git diff --check также прошли.

Исправление entrypoint.sh применяется после пересборки Docker-образа и

локальные; работающий VPS не менялся.

## Кнопки и одновременные действия

Дополнительный прогон: **413 тестов прошли**. Исправлены ещё три сценария:

- Ручная правка оставляла статус pending во время доставки нового варианта.
  Другой участник с правом доступа мог начать публикацию, после чего ошибка
  доставки вызывала откат текста. Теперь пост остаётся regenerating до завершения
  доставки; публикация в этот промежуток получает ответ о занятом посте.
- Подтверждения MAX зависели только от версии поста. Старая кнопка подтверждения
  могла сработать после отмены, если версия не менялась. Теперь подтверждения
  публикации, принудительного повтора и отклонения содержат одноразовый случайный
  идентификатор. Он хранится в существующем dialog_state с привязкой к пользователю
  и базе пространства. Отмена, новая навигация или использование подтверждения
  делают прежнюю кнопку недействительной. При повторном открытии создаётся новое
  подтверждение. Старые кнопки подтверждения без идентификатора просят открыть
  действие заново. Проверки автора, роли, состояния и версии поста сохранены.
- Первые 20 недоступных для редактирования сообщений могли постоянно занимать
  очередь очистки клавиатур. Теперь обход продолжается со следующего сообщения,
  а неудачные удаления повторяются на следующем круге.

Проверены отмена и повторное открытие подтверждения, два одновременных нажатия,
попытка применить подтверждение к другому пространству с совпадающим ID поста,
успех и ошибка доставки ручной правки, а также продолжение очистки после ошибок MAX.

Удаление видимой клавиатуры зависит от ответа MAX: при отказе сервиса старая
клавиатура может временно оставаться в чате. Это не возвращает действие
недействительному подтверждению. При обновлении старые подтверждения нужно открыть
заново через актуальные кнопки поста. Эти исправления входят в Python-код и
применяются обычной кнопкой обновления; новых переменных .env не требуется.
